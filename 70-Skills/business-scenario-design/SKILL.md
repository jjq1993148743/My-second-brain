# 业务梳理 / 功能设计：强制场景推演

## 硬门（HARD GATE）

在产出任何方案、功能清单、原型描述、技术设计之前，必须依次完成下面六步，**每一步都有必填产物，缺一项即视为未完成**。

不允许的跳步理由（出现即违规）：
- 「需求很简单，不用这么细」
- 「先出个大概，细节后面再补」
- 「用户就是普通用户，不用区分」
- 「这是标准功能，场景不用推演」

如果用户主动说「先给个粗的」「不用这么细」，仍然要产出六步，只是每项可以写一行——**但不能省掉任何一项**。宁可一行一项，也不许缺项。

---

## 第一步：角色卡（禁止出现「用户」这个笼统称呼）

列出所有会与这个功能发生关系的人（包括不做操作但会看到结果的人）。每个角色必须填满六格：

| 字段 | 要回答的问题 | 反面示例 |
|---|---|---|
| 身份 | 他在组织/流程里是谁，跟这件事什么关系 | 「用户」 |
| 权限边界 | 他能看什么、能改什么、不能碰什么 | 「有权限的人」 |
| 使用频次 | 每天/每周/每月几次，还是只用一次 | 「经常用」 |
| 熟练度 | 第一次用还是老手，需不需要被教会 | 「会用电脑」 |
| 使用时的真实状态 | 赶时间？被打断？手机单手？在嘈杂现场？旁边有人看？ | 「正常使用」 |
| 他真正想完成的事 | 他的目的，而不是我要他点的按钮 | 「完成下单」 |

**强制要求**：至少包含一个「非操作者角色」（审批人、被通知人、事后查看的人、客服、财务对账的人），并说明他在什么时刻被动卷入。

**禁止项**：角色名不许叫「用户」「管理员」「操作员」这种不带场景的通用词；必须是「门店店长小王，月底对账时用」这种带情境的具名角色。

---

## 第二步：场景流水（每个角色 ≥ 3 条）

每条场景按固定六段写，不许省略任何一段：

```
【场景名】角色 + 时刻 + 目的
触发：什么让他打开这个东西
前置条件：他手上已经有什么、系统里已有什么状态
操作序列：他具体点哪里、填什么、看到什么（一步步，不许写「填写信息」这种合并描述）
系统反馈：每一步之后系统给什么回应（加载中？成功？静默？）
异常分支：这一步可能怎么失败，失败后他看到什么、能做什么
结束状态：他的目的达成了吗？系统里留下什么？
```

**每个角色的 3 条场景必须覆盖**：
1. **顺利路径**（他熟练、一切正常）
2. **新手首次**（他不知道该点哪、填错格式、找不到入口）
3. **出错 / 中断 / 并发** 至少一条（网络断、提交重复、别人同时改了同一条、超时、权限突然没了）

**反简化检查**：如果某条场景的「异常分支」写的是「提示错误信息」，就是不合格——必须写清提示什么话、出现在哪个位置、他接下来能做什么、数据有没有脏掉。

---

## 第三步：状态与数据推演

针对这条流程会碰到的每一份数据，回答五问：

1. **改动哪些数据**：具体到字段级别（不是「修改订单」，是「订单状态从待付款变已付款，支付时间写入当前时间」）
2. **谁有权限改**：哪个角色能触发这个改动，哪个角色只能看
3. **改完别人看到什么**：另一个角色下次打开时，界面上哪里变了，会不会收到通知
4. **撤销怎么办**：改错了怎么回退，回退后历史记录留不留，谁批准才能退
5. **历史留痕**：谁在什么时候改了什么，事后能不能查出来，查的人是谁

**常见遗漏**：只推演了主操作者的数据变化，忘了「被通知方看到什么」和「事后审计的人能查到什么」。

---

## 第四步：边界清单

逐条确认，不适用的写「不适用 + 原因」，不许留空：

- **空数据**：列表为空、第一次进来什么都没有时，界面显示什么
- **超量**：1000 条怎么办、分页还是滚动、导出会不会崩
- **重复提交**：用户连点两次、刷新页面重发、消息重投
- **多人并发**：两个人同时改同一条，谁赢、输的人看到什么
- **权限不足**：他能进来但这个按钮不该给他，界面怎么表现
- **跨角色交接**：A 做完交给 B，B 不在/离职/请假了，流程卡在哪
- **超时与失效**：链接过期、会话超时、草稿还在不在
- **数据格式异常**：粘贴进来的内容带空格/全角/超长/特殊字符

---

## 第五步：反简化硬门自检

交付前逐条自问，任一条为「否」就回去补：

1. 我有没有用过「用户」这个词指代角色？（用了就是没做完）
2. 有没有出现过这些词：**等等、后续可扩展、简单处理即可、一般来说、基本可以、视情况而定、类似地**？（出现即删除并改成具体描述）
3. 每一个功能点，我能不能回答「**不做会怎样**」？答不出来说明这个功能点是拍脑袋加的
4. 有没有哪条流程我只写了顺利路径？
5. 有没有哪个角色我一次都没提到，但他其实会被影响？
6. 我写的操作序列，一个没做过这件事的人照着能不能走通？走不通就是写得太粗
7. 我有没有把「技术上怎么做」当成「用户会经历什么」混在一起写？

---

## 第六步：Gherkin 验收标准

每条场景转成至少一条 Gherkin，**角色必须具名**（不许写「用户」）：

```gherkin
场景：店长小王月底导出对账单时发现数据为空
  假如 小王是首次使用对账功能，当月还没有任何已结算订单
  并且 他在 3 月 31 日 22:00 打开对账页
  当他 点击「导出对账单」
  那么 页面提示「本月暂无可导出的已结算订单」，并给出「查看未结算订单」的入口
  并且 不会生成空文件，也不会报错弹窗
```

**要求**：每条 Gherkin 必须能对应到第二步里的具体一条场景；异常场景也要有 Gherkin。

---

## 输出结构（交付时按这个顺序）

```
一、角色卡（表格，≥2 个角色，含 1 个非操作者）
二、场景流水（按角色分组，每条六段齐全）
三、状态与数据推演（按数据对象分组，五问齐全）
四、边界清单（逐条，不适用要写原因）
五、反简化自检（七问逐条回答）
六、Gherkin 验收标准
七、待确认问题（我拿不准、需要用户拍板的，列出来而不是自己假设）
```

第七项很重要：**不确定的地方要问，不许自己假设一个简化版本糊过去**。

---

## 与其它技能的配合

- **外层骨架用 `brainstorming`**：设计类任务先走「先设计、后动手」，未获批准不写实现代码。
- **本技能是内层必填产物**：brainstorming 负责「不许跳步」，本技能负责「不许简化」。
- **需要正式文档时叠加 `prd-development`**：把本技能的六项产物填进 PRD 的问题陈述、角色、用户故事、验收标准章节。
- **需要画流程/状态图时用 `archify`**：把场景流水和状态机画出来，便于发现缺口。
- **需要拆迭代时用 `user-story-mapping-workshop`**：横轴用本技能的场景顺序当主干。

## 常见失败模式（自查用）

| 症状 | 根因 | 修法 |
|---|---|---|
| 方案写得很顺，但用户一问「那如果……呢」就卡住 | 只推演了顺利路径 | 回第二步补异常分支 |
| 功能列表很长，但说不清谁会用 | 没有角色卡，从功能倒推角色 | 回第一步，先有人再有功能 |
| 写着写着变成技术方案 | 把实现细节当成了用户经历 | 操作序列只写他看到的和做的 |
| 用「后续可扩展」收尾 | 不敢承认这里没想清楚 | 改成「待确认问题」列出来 |
| 每个角色都是「用户」 | 偷懒 | 具名 + 加情境 |
```
